## 用搬家比喻

**做了什么**：把 admin 部门从老办公楼（career-report）搬到新办公楼（admin-hub），新楼挂了新门牌 `/b100`。

**问题**：
1. 搬了家具，但**没通知同事改地址簿**——代码里 22 处硬编码的"老地址"一行没改
2. 老办公楼**还有人在**（服务器上 career-report 老进程没关，nginx 兜底反代到老楼）
3. 同事按老地址寄的快递依然能送达 → 表面"工作正常"
4. 直到自己亲自去新楼办事，发现"咦这装修不像我新做的呀"——bug 暴露

## 4 个小判断叠加（不是某一步致命）

### ① 熬夜做最大的动作
搬办公室这种事放在 4 小时熬夜的最后一步——肯定漏东西。HR 工作里也不会"加完整天班最后一小时签离职合同"，编程同理。

### ② 搬完没"广而告之"
切割代码后没 push（commit 留在本地），相当于内部群里没发"我们部门搬了"。服务器老办公楼一直亮着灯。后面所有 bug 都靠这个老楼"兜底"成立。

### ③ 反复贴新门牌，没查同事地址簿
早上 80 分钟改 5 次配置，每次凭"应该好了吧"提交，**没打开浏览器看真实情况**。就像发了 5 封"新地址通知邮件"但从没问过员工"你收到了吗？"。

### ④ 同一天叠 3 件大事
搬家 + 挂门牌 + 通知客户——任何一件单做都是大事，叠在一起出问题时不知道哪里坏。

## 下次怎么避免

### 立刻能做的

- **A. 改完地址类的东西，立刻自己当用户走一遍** —— 打开浏览器登录一次，不要光看代码 / curl
- **B. 任何"搬家"必须两头同时通知** —— 新地址通 + 老地址不通，两个都成立才算搬完
- **C. 本地用 `npm run build && npm run start` 验证**（不是 dev）—— dev 模式会偷偷帮你修，掩盖 bug
- **D. 同一个问题改 2 次没好 → 停下喊 AI 系统化** 找根因，不要"再试一个"

### 长期习惯

- **E. 一天 ≤ 1 件大事** —— 架构改 / 全局配置 / 上生产，每件吃一天。HR 工作不会同一天处理 5 个员工的离职+调薪+调岗。
- **F. "看起来好了" ≠ "好了"** —— 说不清楚"为什么这次工作了"，那它就是侥幸
- **G. UI 违和感是超能力** —— "咦不对劲"的瞬间立刻深挖，不要忽略。AI 看不出 UI 差别，只有你能。

## 早期警报信号（出现就停）

下次做项目，**出现下面任何一条立刻 STOP**：

1. **凌晨 1 点还在做架构改动** → 疲劳决策，第二天准翻车，留到第二天早上做
2. **改了某个全局配置（basePath / cookie path / 端口）后没在浏览器实测** → 立刻打开 DevTools Network 看 fetch 真实 URL
3. **同一个问题改了 2 次还没好** → 别再试，喊 AI 走 `/investigate` 系统化
4. **新路径能用 + 老路径也能用** → 这是危险的"兼容"，往往是兜底掩盖 bug，**新通 + 老 404 才算切干净**
5. **同一天想做 ≥ 2 件大事** → 拆开做，别叠
